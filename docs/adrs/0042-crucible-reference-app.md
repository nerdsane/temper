# ADR-0042: Crucible reference app — Environments API with full config surface

- Status: Accepted
- Date: 2026-04-11
- Deciders: Temper core maintainers
- Related:
  - ADR-0041: IOA field invariants + cross-invariant parent-field lookups (the platform change this reference app pioneers and first consumes)
  - `reference-apps/crucible/PLAN.md` — the implementation plan that materialised into this change
  - [Anthropic Claude Managed Agents API](https://platform.claude.com/docs/en/managed-agents/overview) — upstream shape being mapped
  - `reference-apps/knowledge-base/` — pattern source for crate layout, cascade tests, and DST tests

## Context

Temper ships with a growing family of reference apps that each exist to demonstrate a vertical slice of the platform on a real domain (ecommerce, oncall, knowledge-base). Two gaps remain unfilled by those apps:

1. **No reference app models an agent-runtime control plane.** The Temper vision document positions the platform as the spec-driven substrate for governed agent applications, but every existing reference app is a traditional CRUD-plus-workflow domain. Developers evaluating Temper for agent infrastructure have no analogue to study.
2. **No reference app needs cross-field validation.** The existing apps get by with state-machine guards and `[[cross_invariant]]` parent-status lookups. ADR-0041 introduced `[[field_invariant]]` and extended `[[cross_invariant]]` for parent-field lookups, but the platform changes shipped without a production consumer, which means the new grammar is unused outside of integration tests.

Crucible closes both gaps by re-implementing a subset of Anthropic's Claude Managed Agents API on top of Temper. The upstream product splits its world into four objects — **Agent**, **Environment**, **Session**, **Event** — and runs sessions inside managed cloud containers with a built-in tool loop, event sourcing, and authorization gates. Temper already provides the verified-entity, event-sourced, Cedar-governed substrate for exactly this kind of thing, so the reference app exists to show the mapping end-to-end.

This ADR scopes **Phase 0: the Environment entity only**. Agent, Session, and Event land in follow-up PRs, each with its own ADR if the modelling decisions warrant it.

## Decision

Ship Crucible as a new workspace member at `reference-apps/crucible` whose Phase 0 slice is the **Environment** entity with the full config surface — both `Local` and `Cloud` config types, both `Unrestricted` and `Limited` networking, `allow_mcp_servers`, `allow_package_managers`, `allowed_hosts[]`, and `packages[]` — plus a hard constraint that rejects `Local` environments that set any of the cloud-only fields.

### Sub-Decision 1: OData-only, no wire-compatible REST facade

All HTTP routes are auto-generated by `temper-server` from the CSDL model at `reference-apps/crucible/specs/model.csdl.xml`. There is no `/v1/environments` shim that mirrors Anthropic's path scheme. Crucible speaks OData `/tdata/Environments` and nothing else.

**Why this approach.** The point of a reference app is to demonstrate the Temper development flow: describe the model, verify it, get HTTP routes for free. A wire-compatibility shim would hide the platform's surface behind a second translation layer and add no pedagogical value. Apps that genuinely need wire compatibility with a third-party API can add their own facade without the reference app doing it for them.

### Sub-Decision 2: `Local` is a first-class config type, not a second-class special case

Anthropic's upstream API supports `Local`, `Cloud`, and `Byoc` config types. Crucible models `Local` and `Cloud`; `Byoc` is out of scope for Phase 0. `Local` is treated as the happy-path config type because Temper runs on the developer's machine and the reference app's primary use case is local development.

**Why this approach.** A reference app that treats its happy path as a second-class exception tells the wrong story about the platform. macOS is the only supported platform for `Local`, implied by how the entity is used rather than modelled.

### Sub-Decision 3: Flattened config + JSON-string metadata

Anthropic's upstream `config` field is a nested object: `config: {type, networking: {type, ...}}`. Temper's CSDL toolchain supports neither `ComplexType` nor map-typed properties. Rather than pioneer CSDL complex-type support for a single reference app, Crucible flattens the nested shape to scalar CSDL properties:

- `config.type` → `ConfigType: EnvironmentConfigType` enum
- `config.networking.type` → `NetworkingType: NetworkingType` enum
- `config.networking.allow_mcp_servers` → `AllowMcpServers: Edm.Boolean` (nullable)
- `config.networking.allow_package_managers` → `AllowPackageManagers: Edm.Boolean` (nullable)
- `metadata: map[string]string` → `Metadata: Edm.String` (nullable, holds JSON)

**Why this approach.** Flattening is lossy for clients expecting the upstream shape, but this app is not a drop-in replacement — it's a demonstration of how Anthropic's concepts map onto Temper's primitives. CSDL `ComplexType` support is a platform-wide concern that belongs to its own ADR and should not be blocked on a reference app.

### Sub-Decision 4: `packages[]` collapses into one child entity with a discriminator

Anthropic's upstream `config.networking.packages` is six parallel arrays keyed by package manager: `{pip: [...], npm: [...], apt: [...], cargo: [...], gem: [...], go: [...]}`. Crucible collapses all six into a single `EnvironmentPackage` child entity with a `Manager: PackageManager` enum discriminator.

Similarly, `config.networking.allowed_hosts: string[]` becomes a child entity `EnvironmentAllowedHost` with an `EnvironmentId` FK and a single `Host: Edm.String` field.

**Why this approach.** Collections of structured data belong in child entities in the relational/OData world. Queryability via `$filter=Manager eq 'Pip'` and `$expand=Packages` on the parent is a free win once the entity is registered. A single discriminator beats six parallel collections because navigation properties, Cedar policies, state machines, and cascade tests all apply once rather than six times.

### Sub-Decision 5: Hard `Local` constraint enforced via `[[field_invariant]]`

Anthropic's upstream API does not reject `Local` + `allow_mcp_servers`; the field is just semantically inert. Crucible explicitly rejects every combination of `ConfigType = Local` and any of the cloud-only fields, demonstrating the `[[field_invariant]]` mechanism from ADR-0041. Three field invariants on the Environment entity:

```toml
[[field_invariant]]
name = "LocalNetworkingMustBeUnrestricted"
when    = { field = "ConfigType", equals = "Local" }
require = { field = "NetworkingType", equals = "Unrestricted" }
message = "Local environments must use Unrestricted networking"

[[field_invariant]]
name = "LocalCannotAllowMcpServers"
when    = { field = "ConfigType", equals = "Local" }
require = { any_of = [
  { field = "AllowMcpServers", absent = true },
  { field = "AllowMcpServers", equals = false },
]}
message = "Local environments cannot set allow_mcp_servers"

[[field_invariant]]
name = "LocalCannotAllowPackageManagers"
when    = { field = "ConfigType", equals = "Local" }
require = { any_of = [
  { field = "AllowPackageManagers", absent = true },
  { field = "AllowPackageManagers", equals = false },
]}
message = "Local environments cannot set allow_package_managers"
```

Two parent-field cross-invariants cover the child entities:

```toml
[[invariant]]
name = "AllowedHostRequiresNonLocalParent"
kind = "hard"
on = "EnvironmentAllowedHost.*"
assert = 'related(Environment, EnvironmentId).ConfigType not in ["Local"]'

[[invariant]]
name = "PackageRequiresNonLocalParent"
kind = "hard"
on = "EnvironmentPackage.*"
assert = 'related(Environment, EnvironmentId).ConfigType not in ["Local"]'
```

**Why this approach.** The hard constraint is the whole point of Crucible as a reference app — it's the feature that distinguishes "demo CRUD app" from "demo of Temper's spec-driven validation surface". A user who wants to see how cross-field validation actually works can read these three field invariants and two cross-invariants and immediately understand the pattern.

### Sub-Decision 6: Four-entity roadmap, ship one entity per PR

Phase 0 ships the Environment entity and its two child entities (`EnvironmentAllowedHost`, `EnvironmentPackage`). Phase 1 ships Agent, Phase 2 ships Session, Phase 3 ships Event. Each phase is an independent PR with its own verification cascade and its own ADR if the modelling decisions warrant it.

**Why this approach.** A single PR for the whole managed-agents surface would be unreviewable. Splitting by entity keeps each PR in the review-size sweet spot and lets the platform-change bundle for ADR-0041 stay focused on Environment, which is the only entity in Phase 0 that needs cross-field validation.

## Rollout Plan

1. **Phase 0 (this PR)** — Ship `reference-apps/crucible` with the Environment, EnvironmentAllowedHost, and EnvironmentPackage specs, the CSDL model, stub Cedar policies, the three test files (cascade, DST, HTTP validation), and workspace membership. Additive — no existing crate is modified.
2. **Phase 1 (follow-up)** — Agent entity, including a many-to-one relationship with Environment.
3. **Phase 2 (follow-up)** — Session entity, including Cedar policies for multi-tenant session governance.
4. **Phase 3 (follow-up)** — Event entity, tying sessions to the event-sourced trajectory record.

## Consequences

### Positive
- First reference app to consume `[[field_invariant]]`, validating the ADR-0041 grammar in a real spec.
- First reference app modelling an agent-runtime control plane, filling a documented gap in the platform story.
- Bounded surface — three entities and one action — keeps the Phase 0 review approachable.
- The `Local` constraint is the smallest non-trivial demo of spec-driven cross-field validation, which is exactly what the platform needs a canonical example of.

### Negative
- Crucible intentionally diverges from Anthropic's upstream shape in five places (flattened config, JSON metadata, packages as discriminator child, allowed_hosts as child, hard `Local` rejection). A user who assumes Crucible is a drop-in replacement will be surprised. The README and this ADR both document the divergences.
- `Byoc` config type is out of scope for Phase 0. If a future user needs it, the enum must be extended and new field invariants written — not a large change, but not free.
- PATCHing an Environment from `Cloud` to `Local` while it has child AllowedHosts or Packages leaves the children in a dangling state relative to the parent-field cross-invariant. The write will reject via the new field invariant on the parent, but if enforcement is bypassed (e.g. admin override), the children would need manual cleanup. Documented as a known limitation.

### Risks
- A user reading Crucible as a reference *for Anthropic's API* rather than as a reference *for Temper's modelling surface* could ship an incompatible client. Mitigation: the README opens with "Crucible is not wire-compatible" and links to the upstream Anthropic docs.
- The hard `Local` constraint is a deliberate divergence from upstream, and could confuse a user copying specs verbatim. Mitigation: every field invariant has a human-readable `message` field that the 409 response surfaces, making the divergence loud at runtime.

## Non-Goals

- **Wire-compatible `/v1/environments` REST facade.** OData-only per Sub-Decision 1.
- **`Byoc` config type.** Enum is extensible; comes back in a future PR if a real user needs it.
- **Deep insert support.** Children are POSTed separately; the `EnvironmentAllowedHost` and `EnvironmentPackage` entity sets accept their own POSTs with an `EnvironmentId` FK. A user who wants single-POST deep insert can add it when the platform supports it.
- **Post-PATCH cross-entity sweep.** PATCHing a Cloud Environment to Local while it still has AllowedHosts or Packages children is rejected at the parent-write step, but the dangling-child sweep is out of scope. A follow-up can walk the navigation graph.
- **Agent, Session, Event entities.** Phase 1–3 follow-ups.
- **Real role-based Cedar policies.** Phase 0 ships permissive stubs; real policies land with Session (Phase 2) where role-based multi-tenant governance becomes non-trivial.
- **CSDL `ComplexType` support.** Platform-wide change, not a reference-app concern.
- **Evolution Engine records / trajectories.** No meaningful unmet intents in a CRUD-only slice.
- **Docker compose, OpenTelemetry collector config, reactions.** Crucible is a spec-and-test reference, not a runnable-server reference; it follows the pattern of `reference-apps/ecommerce` and `reference-apps/oncall`, not the pattern of `reference-apps/knowledge-base` which includes those artifacts.

## Alternatives Considered

1. **Ship the whole managed-agents surface (Agent + Environment + Session + Event) in one PR.** Rejected: unreviewable. Splitting by entity is the standard Temper convention and keeps each PR in a reviewable size.
2. **Model `config` as a CSDL `ComplexType`.** Rejected: CSDL `ComplexType` support is a platform-wide change, and pioneering it for a single reference app inverts the normal flow (platform first, reference app second). Flattening is lossy but local.
3. **Expose `config.networking.packages` as six parallel collections** (`PipPackages`, `NpmPackages`, …) to match Anthropic's shape exactly. Rejected: six parallel state machines and Cedar policies and cascade tests for what is morally one entity with a discriminator.
4. **Skip the hard `Local` constraint and just document the limitation.** Rejected: the hard constraint is the reason Crucible exists as a reference app rather than a generic CRUD demo. Without it there is no cross-field validation story.
5. **Defer Crucible until after Agent + Session + Event are modelled.** Rejected: the Phase 0 scope is already self-contained, and the ADR-0041 platform work it consumes is already in review. Waiting would leave `[[field_invariant]]` with no production consumer indefinitely.
6. **Write Crucible as a separate repository that depends on Temper crates as path dependencies.** Rejected: inconsistent with every other reference app, which all live in `reference-apps/` as workspace members. Workspace membership gives free CI coverage and keeps the reference app in lockstep with platform changes.
